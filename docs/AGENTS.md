# 项目开发准则

## 总则

- 代码首先是写给工程师阅读、审核、调试和维护的。
- 优先使用直接、显式、可顺序阅读的控制流，不为形式统一增加抽象。
- 修改前必须重新读取磁盘上的当前文件，不依赖历史回复、记忆或可能未保存的编辑器缓冲区。
- 同时查看直接依赖、相关调用点和 Git 工作区状态，再判断职责与影响范围。

## 最小功能开发

- 每轮只实现用户明确要求的功能，不为未来可能出现的需求提前设计。
- 模块初始化必须在进入 OS 主循环和启动周期任务之前集中完成。
- 周期函数和运行期业务接口不得调用、重试或懒加载各类 `init` 函数。
- 第一轮未明确要求时，禁止增加：
  - 状态查询接口；
  - 错误查询接口、错误码或错误状态；
  - 超时、重试次数和故障恢复策略；
  - 事件通知；
  - 锁、队列、临界区等并发机制；
  - 扩展框架、配置框架和兼容层。
- 审核问题必须区分为：
  - 阻止当前需求正确工作的功能缺陷；
  - 后续阶段的可靠性或保护增强；
  - 可选的维护性建议。
- 只有第一类问题可以阻塞最小功能实现。不得把可选增强描述成当前必须修复的缺陷。

## 静态职责

- 静态函数和静态变量必须属于实际拥有该职责的最小模块。
- 静态函数满足以下任一条件时应保留：
  - 表达设备级或设备组操作；
  - 表达组合业务条件；
  - 表达独立状态阶段；
  - 保证多个路径执行一致且不能遗漏的操作；
  - 包含有实际意义的策略或判断。
- 静态函数仅有以下行为时应删除或内联：
  - 原样转发参数；
  - 只给一次函数调用或一次比较改名；
  - 只返回常量；
  - 对已经幂等的初始化重复保存状态；
  - 隐藏很短的控制流，却没有增加业务含义；
  - 仅用于让不同设备在形式上看起来统一。
- 不按函数行数判断价值。两行的设备组操作可能有明确职责，较长的参数转换函数也可能只是虚封装。
- 不重复保存下层模块已经拥有的状态，除非新状态具有不同且明确的含义。

## 抽象与重复

- 不机械消除重复代码。
- 当每处代码定义不同业务命令，且显式值能提高可读性时，允许保留重复。
- 打开、关闭、伸出、收回等入口应优先直接显示设备、方向和目标，不必通过通用请求函数转发。
- 只有同时满足以下条件时才提取公共逻辑：
  - 名称和职责单一明确；
  - 消除的是有遗漏或不一致风险的重复；
  - 调用点无需跳转即可理解；
  - 不隐藏具体设备、条件、方向或目标。
- 不因两个流程相似就引入通用设备表、回调、函数指针分发、参数化状态机或公共上下文框架。
- 设备的电机数量、完成条件或控制方式不同时，优先保留各自命名清楚的函数。
- 小型固定状态机优先使用显式 `switch`。没有运行时选择需求时，不使用函数指针表代替少量固定分支。

## 可读性

- 函数名应体现具体设备、动作或状态阶段。
- 变量名应优先体现变量承担的职责，不使用存储类型、作用域或数据类型前缀代替职责名称。
- 不使用 `s_` 表示 `static` 变量；变量的静态作用域由声明本身表达。
- 结构体类型统一使用 `_t` 后缀，枚举类型统一使用 `_e` 后缀。
- 有明确职责名称时，不使用 `ctx`、`cfg`、`dir`、`id`、`ok` 等通用缩写作为变量名。
- 同一类型的不同实例应通过设备、通道或用途区分，例如 `door0_block_monitor`，不通过类型前缀区分。
- 状态分发与设备控制细节应分层，但不增加只做转发的中间层。
- 避免让读者在多个单行辅助函数之间跳转。
- 保留能够概括真实设备组动作或组合条件的领域函数。
- 不为减少行数压缩代码。
- 简单赋值、简单比较，以及参数本身都是简单标识符的函数调用应保持单行，不在赋值符、比较符或参数列表中机械换行。
- 行宽限制不得优先于连续表达式的可读性；语句略长时也不要拆成割裂语义的多行。
- 不添加只是复述代码的注释。
- 通用辅助函数与少量显式代码冲突时，如果显式代码更清楚地展示设备、条件、方向或目标，则选择显式代码。

## 修改流程

修改前：

1. 从磁盘读取当前文件。
2. 阅读直接使用的接口和相关调用点。
3. 检查 Git 工作区状态。
4. 区分用户已有修改与本次任务修改。
5. 明确哪些现有行为必须保持不变。

修改时：

1. 改动限制在当前需求涉及的模块和行为内。
2. 不增加无关接口、保护机制或未来扩展。
3. 不用通用框架替换清楚的设备专用代码。
4. 不覆盖或回退无关的用户修改。

修改后：

1. 重新从磁盘读取结果。
2. 搜索已删除符号，确认没有残留引用。
3. 执行最小范围的语法检查、测试或构建。
4. 将现有依赖警告与本次修改导致的错误分开报告。
5. 确认文件是否被 Git 跟踪，并确认是否已加入工程构建。

## 审核输出

- 先报告与当前需求直接相关的具体问题。
- 不把推测性的后续增强列为强制缺陷。
- 建议删除或保留封装时，必须说明：
  - 它当前承担什么职责；
  - 它增加了业务含义，还是只重命名底层操作；
  - 删除或保留后调用点是否更容易阅读；
  - 是否改变现有行为。
- 没有剩余虚封装时应直接说明，不为缩短文件或追求统一继续删除函数。
